# Assumptions behind the safety guarantees

The paper uses the words "mathematically guaranteed safety", "zero safety violations"
and "100% Zeno-freeness". Each of these holds only under the assumptions below. Outside
them the claims must be read as empirical observations from the simulator.

## 1. System model

- The controlled plant is a single cell. Its configuration vector is
  x = (P_tx [dBm], P_PRB [%], H_HO [dB]) and the actuator input is u.
- The plant is modelled as a first-order integrator, x_dot = u, with f = 0 and g = I.
  This is an approximation of the network's response to configuration changes.
- The stochastic telemetry (PRB utilisation, RSRP fading) is generated by
  Ornstein-Uhlenbeck processes. The filter does not know these processes; it only sees
  the sampled telemetry.

## 2. Validity region of the barriers

- Barrier functions h_i(x) are linear box constraints taken from the configured limits
  (for example P_tx in [5, 46] dBm, matching `llm-agent/intent/config_generator.py`).
  Forward invariance of the box is guaranteed only inside this region.
- The safety guarantee applies to the configuration parameters that the barriers cover.
  Quantities that are not in the state vector, such as interference from neighbouring
  cells or user mobility, are outside the guarantee.

## 3. Lyapunov condition

- The C++ core (`CbfEngine::evaluate_lyapunov`) implements the decrease condition
  V_dot <= -alpha V. The 50-run campaign does not use it.
- The campaign (`gate2_cbf` in `evaluation/statistical_analysis.py`) uses a static check
  instead: V(x) = ||x - x_ref||^2 with x_ref = (30 dBm, 3 dB, 50 %), and an intent is
  denied when V >= 5000. This is a distance threshold, not a decrease condition, and it
  gives no convergence guarantee.
- At V_max = 5000 the check denies no intent of the (corrected) generator; it becomes
  binding below roughly V_max = 3000 (`evaluation/results/vmax_sweep.csv`). Before the fix
  described in `ERRATUM.md` it denied 11,573 nominal intents.
- A per-step continuous-time decrease condition is not meaningful for a sampled loop. The
  journal version replaces it with a discrete-time formulation.

## 4. Delays

- Actuation delay and measurement delay are not part of the evaluated model. The
  guarantees assume they are zero or negligible compared with the actuation interval.
  Any deployment with OsmoBTS round trips above that interval must re-check this.

## 5. "Zeno-freeness"

- In this code, "Zeno-free" means the ZenoGuard minimum inter-actuation interval tau_min
  is never violated (`safety-filter/core/zeno_guard.py`). It is a rate limit on
  actuations, not a continuous-time non-Zeno proof.
- Because the loop is sampled, a Zeno trajectory cannot occur inside the simulated
  loop. The guard is therefore a safety margin against the physical command rate of the
  network element.
- The campaign in `evaluation/statistical_analysis.py` uses TAU_MIN_MS = 200.0, which is
  the value in the paper. The default of `ZenoGuard.tau_min` in
  `safety-filter/core/zeno_guard.py` was 0.5 s in the snapshot and is now 0.2 s, so code,
  campaign and paper agree.
- In the campaign, every intent is separated from the previous one by 0.5 to 3.0 s
  (`run_single_experiment`), so the 200 ms guard can never fire. The 0.0 Zeno-violation
  rate is therefore a consequence of the generator, not evidence of a tested guarantee.
